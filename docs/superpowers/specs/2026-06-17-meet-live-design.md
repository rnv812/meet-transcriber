# meet live — живой ассистент встречи — дизайн

Дата: 2026-06-17. Статус: черновик (на согласовании).

Развитие транскрибатора (`2026-06-12-transcriber-design.md`): помимо записи и
расшифровки постфактум — помощь по ходу встречи. Пользователь подключается к
созвону, запускает живой режим, и Claude по ходу разговора ведёт состояние
встречи и подсказывает (что спросить, что не закрыто), а в конце отдаёт точный
транскрипт и саммари.

## Цель и рамки

- Всё локально и **внутри Claude Code** — без прямых вызовов Anthropic API.
  Слой «ума» = сама сессия Claude Code; расход — внутри подписки.
- Поверхность подсказок — **отдельное окно Claude Code** рядом с окном созвона
  (на втором мониторе). Это сознательное решение: инлайн-вставки в окно созвона
  не делаем.
- Задержка — «почти живой» режим, не мгновенный. Честный потолок ~30–45 с от
  реплики до возможной подсказки (обоснование — в разделе «Латентность»).
- Качество распознавания в онлайне — «достаточное для советов». Эталонный
  транскрипт даёт существующий офлайн-проход в конце встречи.

### Вне рамок первой версии (YAGNI)

- Онлайн-диаризация: дальняя сторона в живом транскрипте — единый «Собеседник»,
  отдельные спикеры не различаются (точная диаризация — офлайн в конце).
- Перекрытие окон со склейкой/дедупликацией (overlap-stitching).
- GUI-оверлей, системные уведомления как обязательная часть (звуковой сигнал —
  опционально, см. ниже).
- Горячая смена аудиоустройства в середине встречи (документируем как «нельзя»).

## Архитектура

Три слоя с чистыми границами:

```
[Python-движок: meet live]                 [Claude Code: окно подсказок]
 WASAPI callback (две дорожки)
   ├─ пишет sys.wav / mic.wav  ────────────────────────────────┐ (для офлайн-прохода)
   └─ tee → потокобезопасная очередь                           │
        │                                                       │
   ASR-воркер (один поток):                                     │
     окно ~20 с → resample 16k моно (scipy) →                   │
     гейн far-end (измерен один раз) → Transcriber →            │
     фильтр галлюцинаций → дозапись строк                       │
        ↓                                                       │
   recordings/<дата>/live_transcript.md ──дайджест~80с──► Claude: │
                                                  ведёт live_state.md,
                                                  выдаёт подсказки,
                                                  отвечает по запросу
                                                        │
   (по «стоп»: release GPU, Event «готово») ◄───────────┘
                                                        ↓
                                          meet transcribe <дата>  (существующий
                                          точный пайплайн с pyannote) →
                                          <дата>_transcript.md + финальное саммари
```

- **Аудио→текст** — целиком в Python-движке.
- **Текст→советы** — целиком в сессии Claude Code.
- **Итоговый артефакт** — существующий офлайн-пайплайн, переиспользуется как есть.

## Компоненты

### 1. `asr.py` — резидентный транскрайбер (рефактор)

Сейчас `transcribe_wav` грузит модель на каждый вызов и удаляет в конце —
для окон каждые 20 с это недопустимо. Выносим состояние:

- Класс `Transcriber`: модель large-v3 грузится **один раз** (`load()`),
  затем `transcribe_window(audio, *, offset_s, hotwords, initial_prompt)`
  принимает numpy float32 16k моно и возвращает `list[Segment]`.
- `offset_s` прибавляется ко всем `start`/`end` сегментов и слов (таймкоды
  Whisper относительны окну — без сдвига попадут в абсолютное время неверно).
- `initial_prompt` = хвост текста прошлого окна (компенсирует потерю
  кросс-оконного контекста; не блокер, но улучшает пунктуацию/термины).
- VAD настраивается под короткое окно (как офлайн: `min_silence` ≈160 мс),
  пустое окно (тишина) — норма, ничего не дописываем.
- Фильтр галлюцинаций: отбрасывать сегменты с высоким `no_speech_prob` /
  низким `avg_logprob` (Whisper фантазирует на тишине/шуме).
- Существующий офлайн `transcribe_wav` переключается на `Transcriber`,
  поведение не меняется (зелёные тесты — критерий).
- `_add_nvidia_dll_dirs()` не трогаем.

### 2. `live.py` — движок живого режима (новый)

- Переиспользует логику записи из `recorder.py`: callback пишет в `WavWriter`
  (как сейчас) **и** докидывает сырые байты в `queue.Queue` на дорожку.
  В callback — никаких вычислений и локов (только запись + append в очередь),
  иначе блокировка аудиопотока и дропы.
- ASR-воркер (один поток): каждые `WINDOW_SECONDS` сливает накопленное аудио по
  каждой дорожке, int16→float32, `scipy.signal.resample` в 16k моно, для far-end
  применяет гейн (см. ниже), вызывает `Transcriber.transcribe_window`, дописывает
  строки `[ЧЧ:ММ:СС] Вы: …` / `[ЧЧ:ММ:СС] Собеседник: …` в `live_transcript.md`
  атомарно (append).
- Один воркер сериализует обе дорожки — ctranslate2 не допускает параллельных
  `generate()` на одной модели; памяти на одну резидентную модель хватает.
- Громкость far-end: измерить RMS один раз по первому окну с реальной энергией
  (тихое стартовое окно гейн не замораживает) и применять фиксированный гейн ко
  всем окнам. Пер-окно не пересчитывать. Закрывает регресс качества far-end (без
  нормализации эталон давал ~на треть меньше текста).
- Таймкоды окон — по wall-clock от старта записи (внедряемые часы); все дорожки в
  такте делят один offset → синхрон даже когда дорожка простаивала.
- Стоп: `threading.Event` → воркер дорабатывает очередь, закрывает wav,
  `Transcriber` выгружает модель (`unload_model()` + `del` +
  `torch.cuda.empty_cache()`), выставляет Event «готово» — чтобы офлайн-проход
  не стартовал при занятой видеопамяти.

### 3. `audio.py` — ресемпл в памяти (дополнение)

- Новые помощники для живого режима: ресемпл numpy в 16k моно (scipy, ~12 мс),
  измерение/применение гейна. Существующий `to_wav16k` (ffmpeg) остаётся для
  офлайн-пути.

### 4. `cli.py` — подкоманда `live`

- `meet live [out_dir]` → запуск движка. Папка `recordings/<дата>/` как у `record`.
- Запускается фоном (не блокирует), чтобы сессия Claude Code могла вести цикл.

### 5. Скилл `/meet-live` — оркестровка в Claude Code

- Preflight: проверить `HF_TOKEN` (нужен офлайн-проходу в конце — иначе упадём
  через час); проверить, что движок стартовал и пишет файл.
- Запустить `meet live` фоном.
- Цикл — НЕ построчно: построчный `Monitor`/`tail` спамит чат и блокирует ответы
  пользователю (подтверждено на пилоте). Вместо этого редкий тихий хартбит-такт
  (~80 с, таймер-тик при росте транскрипта, НЕ построчный) запускает **фоновый
  субагент-дайджестер**: он читает только новый
  хвост `live_transcript.md` (с позиции в `live_state.md`), обновляет состояние и
  возвращает тезисы/вопросы. Чтение скрыто в субагенте, основной цикл свободен →
  пользователь не ждёт. На «стоп» такт не переназначается.
- Вывод — бегущий конспект тезисами (см. ниже), плюс подсказки.
- Health-check: если файл не растёт N тактов — предупредить, предложить рестарт.
- По «стоп»: остановить фон, дождаться Event «готово», запустить
  `meet transcribe <дата>` (точный пайплайн с диаризацией), затем написать
  финальное саммари.

## Поведение ассистента (бегущий конспект + подсказки + по запросу)

Ведёт `live_state.md` (позиция чтения / темы / тезисы / открытые вопросы / решения)
и выдаёт **бегущий конспект** — по одному тезису на ЗАКРЫТЫЙ пункт (обсудили →
решили → дальше), чтобы вывод читался без вслушивания:

    🟢 **<Тема>** — суть → итог/решение
    💡 <открытый вопрос / непокрытый пункт повестки / противоречие>   — если есть

Тезис — на закрытый пункт, не на каждую реплику. 💡 — на повисший вопрос, пробел,
противоречие, или когда пользователь спрашивает. Не повторяет уже выданные тезисы.

Контекст встречи (повестка, цели) попадает в сессию штатно: пользователь в начале
сессии называет задачу, скилл notes-vault подтягивает её контекст. Ассистент
`/meet-live` использует этот контекст из сессии для триггера №3 — отдельного
чтения заметок движком не требуется.

## Поток данных и файлы в `recordings/<дата>/`

- `sys.wav`, `mic.wav` — как сейчас (нужны офлайн-проходу).
- `live_transcript.md` — черновой живой транскрипт (вход для Claude). Остаётся
  на диске как черновик; итог берём из офлайн-прохода.
- `live_state.md` — рабочее состояние ассистента.
- `<дата>_transcript.md` — итоговый точный транскрипт (офлайн).

Живой и итоговый транскрипты **не сливаем**: окна и таймкоды живого режима не
совпадут с полным проходом (другая нормализация, VAD на границах). Живой —
черновик для подсказок, итог — отдельный артефакт.

## Латентность и два регулятора

Слагаемые: наполнение окна (≈WINDOW_SECONDS) + ASR (~1–2 с на 20 с при large-v3,
~5–8% реального времени) + такт чтения Claude + рассуждение. Доминируют **окно**
и **такт чтения**, не ASR. Поэтому разводим два независимых регулятора:

- `WINDOW_SECONDS` движка (дефолт 20; 10–15 уменьшает задержку ценой ошибок на
  границах фраз);
- частота, с которой Claude читает/вмешивается (может быть реже окна).

Ожидание переобозначаем честно: «почти живой конспект + ответы по запросу»,
а не мгновенная подсказка.

## Обработка ошибок

- Callback никогда не блокируется (без вычислений/локов) — иначе дропы аудио.
- Ошибка отдельного окна в воркере: залогировать строкой-комментарием в
  `live_transcript.md`, продолжить (не валить весь режим).
- OOM в ASR: залогировать и остановиться чисто (не молчаливая деградация);
  существующий фолбэк float16→int8 сохраняем.
- Перед офлайн-проходом — гарантированный release видеопамяти + ожидание Event.
- Смена аудиоустройства в середине: на MVP — предупреждение при старте +
  health-check (молчаливое падение рекордера обнаруживается по остановке роста
  файла).
- `HF_TOKEN` — preflight при старте `/meet-live`.
- Коллизия имён `<дата>_transcript.md` для нескольких записей одного дня —
  существующий баг; в рамках этой работы как минимум не усугублять (живые файлы
  лежат внутри `recordings/<дата>/`, не пересекаются).

## Проверка

- Юнит: сдвиг таймкодов (`offset_s`), ресемпл (частота/форма/моно), измерение и
  применение гейна, фильтр галлюцинаций, резидентный `Transcriber` на numpy-массиве.
- Интеграция (без реального GPU, ASR замокан): имитация callback на реальных
  частотах, рост `live_transcript.md`, стоп-handshake, отсутствие дедлоков/дропов.
- Замеры (Фаза 0, на реальном GPU): время large-v3 на окне 20 с; фактические
  частоты устройств; тайминг callback с подключённым tee. Ворота перед циклом.
- Пилот на реальной встрече: задержка, полезность подсказок, расход, видимость
  поверхности; подстройка окна/такта/порога.

## Ключевые решения из риск-анализа (премортем 2026-06-17)

Подтверждено и заложено в дизайн: резидентная модель; сдвиг таймкодов; numpy-вход;
не блокировать callback; release GPU + handshake перед офлайн-проходом; ресемпл в
памяти (scipy); гейн far-end «измерить один раз»; настройка VAD и фильтр
галлюцинаций под короткое окно; тихий хартбит-такт + фоновый дайджестер (НЕ
построчный `Monitor` — выявлено на пилоте); перечитывать `live_state.md` каждый
такт; wall-clock таймкоды; health-check рекордера.

Опровергнуто проверкой (силы не тратим): «condition_on_previous_text зашит в
False» (нерелевантно — `BatchedInferencePipeline` не используется); «дрейф 300 мс
между дорожками» (обе дорожки 48 кГц, дрейф <1 мс); «промах кэша / дорого по
токенам» (непрерывный опрос держит кэш тёплым, и это подписка, не API);
«параллельные дорожки → OOM» (транскрибируем последовательно).

## Открытые вопросы

- Точные дефолты `WINDOW_SECONDS` и такта чтения — подбираются на пилоте.
- Судьба черновых `live_transcript.md`/`live_state.md` после встречи (хранить /
  чистить) — уточнить по итогам пилота.
