# Автозапись встреч Диона: трей-резидент с детектором звонка

Дата: 2026-08-07. Статус: дизайн согласован с пользователем (автозапуск и
автостоп по факту звонка в Дионе, ручной запуск сохраняется, трей становится
резидентным и уезжает в автозагрузку; работает на десктопе и на ноуте).

## Задача

Не вспоминать про запись. Сейчас запись начинается ярлыком «Запись встречи»:
забыл нажать — встреча не записана, вспомнил на середине — потеряно начало.
Надо, чтобы подключение к комнате в Дионе само поднимало запись, а выход из
неё — останавливал её и запускал уже существующий `post_record_hook` (окно
Claude Code с предложением транскрибировать).

При этом ручной запуск остаётся в полном объёме: записать можно не только
конференцию Диона (телефонный разговор, надиктовка, звонок в другом
приложении), и такая запись не должна зависеть от состояния Диона.

## Сигналы: как понять, что идёт звонок

Два независимых признака, опрос раз в `poll_seconds` (по умолчанию 2 с):

### Сигнал A — микрофон занят Дионом

Windows ведёт учёт обращений к микрофону в реестре:

```
HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\CapabilityAccessManager
    \ConsentStore\microphone\NonPackaged\<путь к exe, \ заменён на #>
```

Значения `LastUsedTimeStart` и `LastUsedTimeStop` — FILETIME.

- **Ключ ищется по суффиксу** имени (`#Dion.exe`), а не по полному пути.
  На десктопе это `C:#Users#user#AppData#Local#Programs#Dion#Dion.exe`, на
  ноуте путь может отличаться — суффиксный поиск даёт один код на обе машины.
- **«Занят» = `LastUsedTimeStop == 0` ИЛИ `LastUsedTimeStart > LastUsedTimeStop`.**
  Два условия, а не одно: обнуление `Stop` на время использования — известный
  механизм Windows, но на машине пользователя вживую не наблюдалось (замер
  2026-08-07 поймал уже закрытый интервал 11:29:54→11:34:34). Правило верно
  при любом из двух поведений и не требует выбирать заранее.

### Сигнал B — Дион что-то воспроизводит

Активная WASAPI render-сессия (`AudioSessionState.Active`) у любого процесса с
именем `Dion.exe`. Нужен против мьюта: если Дион на выключенном микрофоне
закрывает поток захвата, сигнал A пропадёт посреди встречи, а B держится, пока
слышно собеседников.

Реализация — `pycaw` (+ `comtypes`) в зависимостях. Ручной ctypes-COM через
`IAudioSessionManager2`/`IAudioSessionEnumerator`/`IAudioSessionControl2` (как
сделан `IMMDeviceEnumerator` в `recorder.py`) дал бы то же самое без новой
зависимости, но это ~100 строк vtable-кода по трём интерфейсам против пяти
строк на pycaw; на фоне torch/pyannote вес зависимости незаметен.

**Деградация:** `pycaw` не импортировался — вотчер пишет в лог предупреждение и
работает по одному сигналу A. Не падает и не блокирует запись.

### Решение

`в_звонке = A or B`. Обе проверки — чистые функции от прочитанных значений,
тестируются без запущенного Диона.

## Компоненты

### 1. `src/meet/watch.py` — детектор и стейт-машина

Отделён от трея: детектор не знает про pystray, трей не знает про реестр и COM.

- `mic_busy(exe_suffix) -> bool | None` — сигнал A (`None` = ключа нет).
- `render_active(process_name) -> bool | None` — сигнал B (`None` = pycaw нет).
- `Watcher` — стейт-машина с грейсом, принимает текущее время параметром
  (инъекция для тестов), возвращает решение: `START`, `STOP`, `NONE`.

Состояния и переходы:

| Из | Событие | В | Решение |
|---|---|---|---|
| idle | `в_звонке` стало true | recording | `START` |
| recording | `в_звонке` стало false | grace | `NONE` |
| grace | `в_звонке` стало true | recording | `NONE` (грейс сброшен) |
| grace | прошло `grace_seconds` | idle | `STOP` |

Стейт-машина отслеживает намерение, а не факт: если по `START` запись не
поднялась (ошибка устройства), состояние всё равно станет `recording`, и по
выходу из звонка придёт `STOP` на несуществующую запись — трей его игнорирует.

**Во время грейса запись продолжает идти.** Это ключевое: выкинуло из комнаты
на две минуты по сети — таймер тикает, вернулся — сброшен, файл цельный, внутри
пара минут фона (VAD его в транскрипт всё равно не пустит). Порвётся запись
только если разрыв длиннее грейса, отсюда щедрые 180 с по умолчанию.

### 2. Трей становится резидентным (`src/meet/tray.py`)

Сейчас `meet-tray` начинает запись сразу при старте и завершает процесс после
остановки — в автозагрузку такой поставить нельзя. Разделяется на два состояния
внутри одного процесса:

| Состояние | Иконка | Тултип | Меню |
|---|---|---|---|
| Дежурный | серый круг | «Жду встречу» | «Начать запись», «Выход» |
| Запись | синий круг (как сейчас) | «Запись: MM:SS» | «Остановить запись», «Отменить (удалить)» |

- Переход в запись и обратно — без перезапуска процесса. Поток записи и
  `stop_event` создаются на каждую запись заново.
- «Остановить запись» — как сегодня: штатная финализация, уведомление с папкой,
  `_launch_claude(folder)`.
- «Отменить (удалить)» — стоп плюс удаление папки записи, `post_record_hook`
  не вызывается. Это выход для случая «автозапустилось на том, что писать не
  надо».
- Ошибка старта записи — уведомление, возврат в дежурное состояние (а не выход
  процесса, как сейчас).

### 3. Единственность и ручной запуск

`%LOCALAPPDATA%/meet/tray.lock` — JSON `{"pid": ...}`, живость pid проверяется
тем же `OpenProcess`-приёмом, что и lock записи (`os.kill(pid, 0)` на Windows
использовать нельзя — это TerminateProcess).

Запуск `meet-tray`:

- дежурный жив → записать `start` в `%LOCALAPPDATA%/meet/command` и выйти молча;
- дежурного нет → стать дежурным. Если запуск был из ярлыка (аргумент
  `--record`) — сразу начать запись, как сегодня.

Дежурный раз в секунду проверяет файл команды: прочитал → удалил → выполнил.
Так ярлык «Запись встречи» продолжает работать привычно и при живом резиденте,
и без него. Команда `start` при уже идущей записи → уведомление «Запись уже
идёт (папка ...)».

### 4. Автозапись не мешает ручной

У записи есть источник: `auto` или `manual`.

- **Автостоп применяется только к `auto`.** Запись, начатая ярлыком или пунктом
  меню, детектор не останавливает никогда — иначе надиктовка или телефонный
  разговор оборвались бы просто потому, что в Дионе нет конференции.
- Детектор увидел звонок, а запись уже идёт (любого источника) → ничего не
  делает. Двух записей одновременно не бывает.

### 5. Лог — основной инструмент разбора

`%LOCALAPPDATA%/meet/watch.log`, строка с локальной меткой времени на:

- каждое изменение любого из сигналов (`A: свободен→занят`, `B: нет→активна`);
- каждое решение (`старт записи (auto)`, `грейс пошёл`, `грейс сброшен`,
  `стоп по грейсу`, `отменено пользователем`);
- heartbeat раз в минуту с текущими значениями A и B.

**Лог пишется независимо от `auto_record.enabled`** — можно неделю смотреть на
поведение сигналов, не давая вотчеру трогать запись. По нему же разбирается
первая живая встреча: видно, отпускает ли Дион микрофон на мьюте и подхватил ли
это сигнал B.

Ротация примитивная: файл перевалил 1 МБ — переименовать в `watch.log.old`
(один бэкап), начать заново.

### 6. Конфигурация

`%LOCALAPPDATA%/meet/config.json`, рядом с существующим `post_record_hook`:

```json
{
  "post_record_hook": true,
  "auto_record": {
    "enabled": true,
    "processes": ["Dion.exe"],
    "grace_seconds": 180,
    "poll_seconds": 2
  }
}
```

Секции нет → вотчер молча спит, трей работает как дежурный с ручным запуском.
Значения по умолчанию совпадают с показанными.

**Машины отличаются ровно одним флагом.** На десктопе `post_record_hook: true`
— после остановки открывается окно Claude Code с предложением транскрибировать.
На ноуте `post_record_hook: false`: транскрибация там не идёт (дискретной GPU
нет, только интегрированная Radeon 860M), запись просто ложится в
`recordings/` и разбирается на десктопе после того, как её оттуда заберут.
Автозапись, автостоп, обе иконки и ручной запуск на ноуте работают ровно так
же, как на десктопе.

### 7. Автозагрузка

Ярлык на `meet-tray.exe` (без `--record`) в `shell:startup`. Готовая
powershell-команда создания — в README, рядом с существующей командой для
ярлыка на рабочем столе.

### 8. Ноут

Тот же код, тот же ярлык, та же автозагрузка. Состояние ноута:

- проект, venv и `meet-tray.exe` на месте, структура зеркалит десктоп;
- Дион установлен по тому же пути (`%LOCALAPPDATA%/Programs/Dion`), ключ
  `#Dion.exe` в ConsentStore присутствует и выглядит так же;
- `pycaw`, `comtypes` и `psutil` в venv установлены;
- `%LOCALAPPDATA%/meet/config.json` отсутствует — **создать при выкатке** с
  `post_record_hook: false` и `auto_record.enabled: true`. Без файла не
  включится ни автозапись, ни что-либо ещё;
- папка автозагрузки пуста — ярлык на дежурный трей туда кладётся при выкатке.

Пути на ноуте совпадают с десктопными, но суффиксный поиск ключа реестра всё
равно оправдан: он снимает зависимость от места установки Диона на будущее.

## Что НЕ делаем

- Другие площадки (Teams, Телемост, Дион в браузере). Конструкция расширяется
  списком `processes` в конфиге, когда понадобится.
- Эвристики «рабочая встреча или личная», сверка с календарём на старте записи.
  Лишнее удаляется пунктом «Отменить (удалить)».
- Пауза/возобновление, хоткей, транскрибация из трея — как и в прошлой спеке.
- Автоматическая транскрибация без участия человека: `post_record_hook`
  по-прежнему только предлагает.

## Обработка ошибок

- `pycaw` не встал → лог-предупреждение, работа по сигналу A.
- Ключа `#Dion.exe` в реестре нет (Дион ни разу не брал микрофон) → сигнал A
  даёт `None`, решение принимается по B; оба `None` → вотчер спит и пишет об
  этом в лог раз в минуту, ничего не запускает.
- Чтение реестра или перебор сессий бросило исключение → поймать, записать в
  лог, считать сигнал `None`. Опрос не должен ронять трей.
- Запись не стартовала (нет устройства, lock занят) → уведомление, возврат в
  дежурное состояние; повторной попытки на том же звонке не делаем, чтобы не
  спамить уведомлениями.
- `tray.lock` с мёртвым pid → перезаписывается новым дежурным.

## Тестирование

Юниты (`pytest -q`, без Диона, реестра и COM — значения подаются напрямую):

- правило «занят»: `Stop == 0`; `Start > Stop`; `Start < Stop` → свободен;
  отсутствие значений → `None`;
- суффиксный поиск ключа: находит при отличающемся префиксе пути, не находит
  при чужом имени exe;
- стейт-машина: старт по появлению звонка; отсутствие второго старта при уже
  идущей записи; грейс не останавливает раньше `grace_seconds`; возврат внутри
  грейса сбрасывает таймер и не даёт `STOP`; `STOP` ровно один раз по
  истечении; запись с источником `manual` не останавливается никогда;
- деградация: `render_active` вернул `None` → решение принимается по A.

Приёмка руками (единственный способ проверить связку целиком) — сценарий
пользователя: зайти в комнату Диона, поговорить, замьютиться на ~5 минут,
выйти. Ожидания: запись поднялась сама в момент входа; мьют её не остановил;
после выхода запись остановилась через 180 с и открылось окно Claude Code с
предложением транскрибировать; в `watch.log` видно поведение обоих сигналов на
мьюте. Отдельно: ручной запуск ярлыком при живом резиденте; ручная запись не
останавливается при отсутствии звонка в Дионе; «Отменить (удалить)» удаляет
папку и не открывает Claude.
